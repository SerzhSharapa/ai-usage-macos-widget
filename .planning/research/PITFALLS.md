# Pitfalls Research

**Domain:** Нативное macOS-приложение (SwiftUI + WidgetKit) — виджет и строка меню с расходом лимитов AI-подписок (OpenAI/Codex, Kimi Code, Z.ai GLM, OpenRouter); токены в Keychain; личная сборка с бесплатным Apple ID
**Researched:** 2026-10-11
**Confidence:** HIGH для эндпоинтов (локальный референс `@linxin666/dsh-usage`, проверен владельцем 11.10.2026 + ≥3 независимых реализации), MEDIUM для платформенных нюансов бесплатной подписи (таблица capabilities Apple извлечена машинно, срок жизни профиля — консенсус сообщества)

**Фазы в тексте** — функциональные: **Ф-0 «Каркас и подпись»** (проект, таргеты, entitlements, сборка), **Ф-1 «Движок опроса»** (адаптеры провайдеров, CLI-проверяемые), **Ф-2 «Учётные данные»** (Keychain + настройки), **Ф-3 «Виджет»** (App Group, TimelineProvider), **Ф-4 «Строка меню»**, **Ф-5 «Документация»**. Roadmap отображает их на свои фазы по таблице в конце.

## Critical Pitfalls

### Pitfall 1: Бюджет WidgetKit принят за гарантию свежести — виджет «врёт» про данные

**What goes wrong:**
Разработчик ждёт от `TimelineReloadPolicy.after(now + 15 мин)` реального обновления раз в 15 минут. Система даёт виджету **40–70 перезагрузок в сутки** (~15–60 мин, интервал плавает), бюджет 24-часовой и подстраивается под поведение пользователя, окно не сбрасывается ровно в полночь. Итог: виджет показывает проценты 40-минутной давности без всякого признака этого, владелец не понимает, почему «0%» не меняется.

**Why it happens:**
Документация Apple говорит «примечательно», но читается по диагонали; в Xcode-отладчике бюджет **не действует** («WidgetKit does not impose this limit when debugging»), поэтому в разработке всё «обновляется часто», а после запуска вне отладчика — нет. Ещё ловушка: записи таймлайна ближе ~5 минут система схлопывает.

**How to avoid:**
1. Проектировать данные как «снимок + возраст»: каждый entry несёт `fetchedAt`, вьюха рисует «данные на 14:32» — требование проекта про возраст кэша.
2. Таймлайн из нескольких записей с большим шагом (15–30+ мин), политика `.after(nextCheck)`, не чаще ~5 мин.
3. Обратный отсчёт до сброса окна рендерить динамической датой (`Text(resetDate, style: .relative)`) — он тикает сам, без перезагрузок и без бюджета.
4. `WidgetCenter.reloadTimelines(ofKind:)` вызывать из приложения после успешного опроса (не по таймеру) — это не тратит бюджет, когда приложение на переднем плане.
5. Приёмку фазы виджета проводить **вне Xcode-отладчика**: собрать, закрыть Xcode, добавить виджет, проверить интервалы обновления.

**Warning signs:**
Виджет обновляется в Xcode-прогоне, но «замер» после обычного запуска; в логах `getTimeline` вызывается реже, чем запрошено; пользователь/владелец жалуется на «застывшие» проценты.

**Phase to address:** Ф-3 «Виджет» (проектирование entry/кэша), приёмка — вне отладчика.

### Pitfall 2: OAuth-токен Codex протух, а «0%» или гонка за refresh-токеном вместо внятной ошибки

**What goes wrong:**
`chatgpt.com/backend-api/wham/usage` принимает **не API-ключ**, а OAuth access token из `~/.codex/auth.json` (`Authorization: Bearer`, заголовок `ChatGPT-Account-Id`, UA `codex-cli`). Access token истекает; наивная реализация показывает «0%» при 401 — худший ложный сигнал для виджета лимитов. Хуже: если приложение пытается само обновить токен через `auth.openai.com/oauth/token` параллельно с Codex CLI, refresh-токен **ротируется** — второй вызов со старым токеном ловит `refresh_token_reused`/`invalid_grant` и разлогинивает пользователя в CLI.

**Why it happens:**
Коденджеры (Codex CLI, Kimi CLI) владеют циклом refresh и файлом `auth.json`. Сторонний опросщик — гостевой читатель. Оба референса это зафиксировали: dsh-usage при 401 пишет «use Codex once and refresh», CodexBar построил целую архитектуру read-only чтения (usage-путь «must not redeem any shared refresh token or write a replacement file»).

**How to avoid:**
1. Позиция «read-only»: токен хранится в Keychain (вставлен пользователем или прочитан из `auth.json`), приложение **никогда** не вызывает refresh и не пишет `auth.json`.
2. 401/истечение → явное состояние «токен протух: запустите codex / вставьте свежий токен», отдельное от сетевой ошибки и от 403.
3. Если когда-нибудь решите делать refresh: единственный владелец записи, лок, обработка кодов `refresh_token_expired` / `refresh_token_reused` / `invalid_grant` / `refresh_token_invalidated`; endpoint `https://auth.openai.com/oauth/token`, client_id Codex CLI `app_EMoamEEZ73f0CkXaXp7hrann`, `grant_type: refresh_token`. Для MVP — не делать.
4. Свежесть оценивать по JWT `exp` access-токена (5-минутный запас как в CodexBar) — можно предупреждать заранее, до 401.
5. UA: референсы используют `codex-cli` (dsh-usage) и собственный `CodexBar` — оба работают; generic UA (curl/стандартный URLSession) может ловить Cloudflare-блок (см. Pitfall 8). Машинно проверить фактический запрос в Ф-1.

**Warning signs:**
Виджет показывает 0% при живой подписке; после недели работы Codex перестал «видеть» виджет; при попытке refresh пользователь разлогинился в codex CLI.

**Phase to address:** Ф-1 «Движок опроса» (классификация 401/403), Ф-2 «Учётные данные» (текст ошибки и сценарий обновления токена).

### Pitfall 3: Жёсткое декодирование ответов — схема drift ломает весь провайдер

**What goes wrong:**
Реальные ответы не стабильны: в тестах CodexBar декодер падает на новом тарифе `unknown variant 'prolite'` (enum plan_type); подокна `primary_window`/`secondary_window` приходят **явно null** («the upstream returns an explicit `null` window when the slot is unused»); у Kimi окно может отсутствовать; у GLM добавляются новые `type`/`unit`. Один незнакомый вариант enum → весь снимок провайдера = ошибка, хотя 90% данных были валидны.

**Why it happens:**
Соблазн описать Codable-структуры 1:1 по первому успешному ответу. Все эти API недокументированные/полудокументированные, серверы меняются без предупреждения.

**How to avoid:**
1. `plan_type`, `membership.level`, `level` — только `String`, не enum; варианты тарифов рендерить как есть.
2. Все окна — опциональные; парсер обрабатывает null/отсутствие как «нет окна», а не «ошибка».
3. Парсить «по смыслу полей», а не по позиции: ключ окна у GLM — по коду `unit` (3=5ч, 6=неделя, 5=месяц), у Kimi — по `window.duration`/`timeUnit` (duration=300 + TIME_UNIT_MINUTE = 5ч), у Codex — по `limit_window_seconds` (18000=5ч, 604800=неделя). Референс dsh-usage делает именно так — «an added or reordered limit cannot shift a window's meaning».
4. Фикстуры реальных ответов в тесты + «упавший» ответ добавлять как новую фикстуру, не чинить парсер вслепую.
5. GLM: строки `TIME_LIMIT` (MCP-запросы) — не окно лимита, пропускать; `success !== true` → не парсить.

**Warning signs:**
Всё работало, после очередного рабочего дня один провайдер стабильно «ошибка» при живом аккаунте; в сыром ответе (лог) видно новое значение поля.

**Phase to address:** Ф-1 «Движок опроса» (парсеры + фикстуры).

### Pitfall 4: Keychain-доступ ломается после пересборки/переподписи (и не чинится `kSecAttrAccessible`)

**What goes wrong:**
При бесплатной команде проект пересобирается часто (см. Pitfall 5), подпись меняется → designated requirement айтема ACL не совпадает → чтение либо падает (`errSecItemNotFound`/-25300), либо сыплет системными промптами «…wants to access your keychain». Типичная неверная «починка» — менять `kSecAttrAccessible`: CodexBar прямо документирует, что этот атрибут «is not a repair mechanism for a legacy file-keychain ACL or for a code-signature/designated-requirement mismatch».

**Why it happens:**
macOS держит два хранилища: legacy file-keychain (с ACL по подписи) и data-protection keychain. Дефолтные запросы `SecItemAdd` на macOS уходят в file-keychain, где доступ привязан к кодовой подписи конкретного билда.

**How to avoid:**
1. Использовать data-protection keychain: `kSecUseDataProtectionKeychain: true` во **всех** запросах (add/read/update) — она не завязана на file-ACL.
2. Общая access group (`keychain-access-groups`) на обоих таргетах, если виджету всё же нужен доступ — но для этого проекта **виджет не должен читать Keychain вовсе** (ограничение PROJECT.md: ключи не попадают в сам виджет): приложение опрашивает провайдеры и кладёт снимок в App Group, виджет только читает снимок. Это устраняет весь класс проблем разом.
3. Токены вставлять через окно настроек приложения, а не через временную заглушку «в код»; после переподписи — ожидаемый сценарий «переввести токен» в UI (см. Recovery).
4. Никогда не писать секреты в UserDefaults/логи при отладке повреждённого Keychain — именно в этот момент их проще всего засветить.

**Warning signs:**
После пересборки приложение просит доступ к собственному айтему или «забывает» токены; `SecItemCopyMatching` возвращает -25300 при заведомо существующем айтеме; промпты Keychain во время фонового опроса.

**Phase to address:** Ф-2 «Учётные данные» (kSecUseDataProtectionKeychain с первого дня), Ф-0 (архитектурное решение «виджет без Keychain»).

### Pitfall 5: Бесплатная личная команда: entitlements, 7-дневные профили и «работает только из Xcode»

**What goes wrong:**
Три отдельных ловушки бесплатного personal team («Apple Developer» без программы):
1. **Capabilities**: доступны App Groups, App Sandbox, Hardened runtime, Keychain sharing, Maps (таблица Apple, извлечена машинно 11.10.2026); НЕ доступны push, iCloud, Network/System extensions, Sign in with Apple. Если что-то из недоступного случайно включено — подпись таргета падает загадочной ошибкой provisioning.
2. **Профили личной команды живут ~7 дней** (консенсус сообщества; для iOS это давно норма, для macOS поведение то же для embedded-профиля). Через неделю приложение/виджет перестаёт запускаться с ошибкой provisioning — «было же всё нормально».
3. **App Group id при бесплатной команде префиксуется командой** (`TEAMID.group.…`); вписанный руками «красивый» group id не подписывается. Плюс entitlements должны совпадать на **обоих** таргетах (app + widget extension) — иначе Pitfall 6.

**Why it happens:**
Automatic signing скрывает механику; а премодерации идентификаторов у бесплатной команды нет, часть действий (ручная регистрация App Group в портале) попросту недоступна.

**How to avoid:**
1. Включать только нужные capabilities: App Sandbox + App Groups (+ nothing else) на обоих таргетах; App Group создавать через Xcode (Signing & Capabilities), а не руками — Xcode сам подставит team-префикс.
2. Один скрипт сборки `xcodebuild -scheme … build` с самого начала (Ф-0): «оживить» проект после истечения профиля = одна команда, без мышиных кликов в Xcode.
3. В README (Ф-5) честно зафиксировать: личная сборка, бесплатная подпись, пересборка раз в ~неделю — известное свойство, не баг.
4. Не promises про автозапуск/логин-айтемы, требующие платных capabilities.

**Warning signs:**
Через ~7 дней: `errSecMissingEntitlement`, «provisioning profile has expired», виджет пуст, приложение не стартует вне Xcode; при сборке — «requires a provisioning profile with the App Groups feature».

**Phase to address:** Ф-0 «Каркас и подпись» (целиком), приёмка — запуск собранного вне Xcode спустя >7 дней после предыдущей сборки.

### Pitfall 6: App Group контейнер «пустой» в виджете — entitlements/суиты не совпали

**What goes wrong:**
Приложение пишет снимок, виджет читает пустоту: `UserDefaults(suiteName:)` молча возвращает рабочий дефолт **без** App Group (данные остаются в песочнице процесса-писателя), `containerURL(forSecurityApplicationGroupIdentifier:)` возвращает nil (форс-анрап → краш). Варианты причины: entitlement на одном таргете, разные строки suite, включённый App Sandbox только у виджета, ручной group id без team-префикса (не подписался — Pitfall 5).

**Why it happens:**
API не кричит об ошибке: `UserDefaults(suiteName:)` без entitlement не возвращает nil и не логирует ничего — просто каждая сторона видит свою «пустую» вселенную.

**How to avoid:**
1. Один источник констант: suite-строка и ключи — в общем SwiftPM-модуле, не в двух местах строками.
2. При чтении: guard на nil `containerURL`/`UserDefaults` с явной ошибкой; при старте виджета — самопроверка «контейнер доступен, файл снимка читается».
3. Писать снимок атомарно (tmp + rename) — виджет может читать в момент записи; формат — маленький JSON с `fetchedAt` и списком окон.
4. Проверка равенства entitlements обоих таргетов включить в приёмку Ф-0 (`codesign -d --entitlements :-` на оба бинаря — suite должен совпадать байт-в-байт).

**Warning signs:**
Виджет в галерее показывает placeholder навсегда; в приложении данные есть, в виджете «нет данных»; nil при форс-анрапе `containerURL` в логах крашей.

**Phase to address:** Ф-0 (entitlements), Ф-3 «Виджет» (атомарная запись снимка).

### Pitfall 7: Z.ai — два происхождения, «голый» ключ без Bearer и чужие окна

**What goes wrong:**
Четыре независимые ошибки из одного семейства:
1. **Ключ-к-хосту привязан**: аккаунт GLM Coding Plan живёт ЛИБО на `open.bigmodel.cn` (Китай), ЛИБО на `api.z.ai` (международный) — путь одинаковый (`/api/monitor/usage/quota/limit`), ключи взаимно не работают. Прозвон чужого хоста = 401.
2. **Авторизация — «голый» ключ без префикса `Bearer `** (в отличие от всех остальных провайдеров проекта): `authorization: <key>`. Добавленный по привычке Bearer = 401.
3. План идёт по `unit`-кодам (3=5ч, 6=неделя, 5=месяц) и типам строк; строка `TIME_LIMIT` — это MCP-запросы, не окно лимита: попав в выборку, она рисует виджету лишнее «окно».
4. CREDIT-планы: точный процент = `currentValue`/`usage`, поле `percentage` — запасной вариант; nextResetTime приходит в смешанных форматах (число/строка epoch, ISO).

**Why it happens:**
Z.ai и bigmodel выглядят как «один провайдер с двумя зеркалами», но это два аккаунт-пространства; а у их API диалект авторизации отличается от OpenAI-совместимого.

**How to avoid:**
1. Хранить с ключом метку происхождения (`open.bigmodel.cn` / `api.z.ai`) — выбор хоста автоматом, не ручной тумблер (CodexBar решает это роутером по региону).
2. Парсер — строго по dsh-usage: `success === true`, `TOKENS_LIMIT`/`CREDIT_LIMIT` — окна, `TIME_LIMIT` — пропуск, ключ окна по `unit`, unknown unit — пропуск строки, не «окно по умолчанию».
3. Заголовок `accept-language: en-US,en` — сообщения и, по наблюдению референса, стабильнее формат ответа.
4. Нормализация времени одна на все провайдеры: epoch-секунды/миллисекунды (число и строка-из-цифр) и ISO → единый Date (см. Moderate №3).

**Warning signs:**
401 на оба хоста подряд (ключ от другого происхождения); в виджете появилось четвёртое «окно» с маленькими процентами (это TIME_LIMIT); проценты «скачут» (percentage vs точного ratio).

**Phase to address:** Ф-1 «Движок опроса» (адаптер Z.ai), Ф-2 (хранение происхождения рядом с ключом).

## Moderate Pitfalls

### Pitfall: Kimi — точный путь и два режима аутентификации

**What goes wrong:** Путь `/coding/usages` без `/v1` реально возвращает 404 (зафиксировано в sub2api: «无 /v1 的 /coding/usages 实测 404») — только `https://api.kimi.com/coding/v1/usages`. Плюс у Kimi два мира: API-ключ (Bearer) и аккаунт Kimi Code CLI (OAuth-токен с обновлением через `auth.kimi.ai/api/oauth/token`, заголовки вида `X-Msh-Platform`); хосты тоже двоятся: `api.kimi.com` (CN) и `api.kimi.ai` (международный).
**Prevention:** Путь — строковая константа «никогда не выводить из base-url окружения» (приём oh-my-claudecode); в Ф-1 зафиксировать один поддерживаемый режим — API-ключ + `api.kimi.com`, OAuth CLI-токена сознательно out of scope (см. Open Questions); при 401 — тот же паттерн «запусти CLI один раз / обнови токен» (готовый текст у codeburn: «Login expired. Run the Kimi CLI once, then refresh»).

### Pitfall: OpenRouter — перепутаны баланс аккаунта и расход конкретного ключа

**What goes wrong:** `/api/v1/credits` возвращает **аккаунтные** `total_credits`/`total_usage` — остаток надо считать самому (`credits − usage`, как в dsh-usage). `/api/v1/auth/key` возвращает другое: usage/limit конкретного ключа, `is_free_tier`, rate-limit-инфо. Проекты путают эндпоинты и показывают «остаток ключа» вместо баланса; часть клиентов держит fallback-стратегию на случай отказа credits (CodexBar: OpenRouterCreditsFallback). Без Bearer — 401 `No cookie auth credentials found` (проверено живым запросом 11.10.2026).
**Prevention:** Один эндпоинт `/api/v1/credits` + явная формула в адаптере; 401 классифицировать как «ключ не задан/неверный», не как сетевую ошибку; fallback на `/api/v1/auth/key` — только если понадобится per-key лимит (сейчас out of scope).

### Pitfall: `getSnapshot` ходит в сеть → галерея и первое добавление висят

**What goes wrong:** `getSnapshot(in:)` вызывается в том числе для галереи виджетов (`context.isPreview`); сетевые запросы на 4 провайдера там недопустимы — система ждёт быстро, иначе показывает заглушку и занижает доверие/бюджет. `getTimeline` обязан вызвать `completion` **всегда**, даже при ошибке (забытый completion = виджет навсегда в placeholder до следующей перезагрузки).
**Prevention:** Snapshot/placeholder — только из кэша App Group, при `isPreview` — семпл-данные; в `getTimeline` при ошибке возвращать снимок-кэш с флагом устаревания (это же требование PROJECT.md); таймауты URLSession 10–15 сек на провайдера, параллельные запросы.

### Pitfall: Смешанные форматы времени сброса

**What goes wrong:** Codex — `reset_at` в unix-секундах; Kimi — `resetTime` (ISO или epoch-строка «1756428000»); GLM — `nextResetTime` (ISO/epoch). Наивный `Date(isoString:)` на строке-epoch даёт nil → «Invalid Date» / пустая ячейка; путаница секунд/миллисекунд сдвигает сброс на годы (значение < 1e12 — секунды, ≥ — миллисекунды; референс dsh-usage нормализует именно так).
**Prevention:** Один нормализатор `toIso()`-стиля на весь проект: число (и строка из цифр) → epoch с эвристикой s/ms, иначе ISO-парсинг, иначе nil; nil → не рисовать «сброс», а показывать «—». Тесты на все три формата.

### Pitfall: Меню-бар компенсирует бюджет — но убивает его же вызовами reloadTimelines

**What goes wrong:** Правильная идея проекта (частая свежесть в строке меню) легко выворачивается наизнанку: каждое обновление в `MenuBarExtra` (раз в минуту, при открытии меню, на каждый tick таймера) дёргает `WidgetCenter.reloadTimelines`. Виджет расходует бюджет вхолостую, к концу дня стоит намертво.
**Prevention:** Меню-бар — самостоятельное представление общего сборщика (как решено в PROJECT.md): свой таймер/поллинг в процессе приложения, а reloadTimelines — только один раз после успешного полного опроса и только если хотя бы одно окно реально изменилось. Стиль `MenuBarExtra` с `.menu` для простого списка или `.window` для карточки — решить в Ф-4, не смешивать.

## Minor Pitfalls

### Pitfall: Логи и публичный репозиторий как канал утечки токенов
**Prevention:** В логи — только префиксы/хэши токенов; NSError-описания URLSession не печатают заголовки, но свои `print(request)` — печатают: не логировать URLRequest целиком; фикстуры для тестов — только синтетические; перед пушем в публичный GitHub — grep по `sk-`, `eyJ`, `Bearer ` в истории.

### Pitfall: Проценты без clamp и семантика «used vs remaining»
**Prevention:** Все проценты clamp 0…100 (референс dsh-usage делает это везде); помнить, что у части провайдеров поле означает «осталось» (в семьях-соседях вроде MiniMax — remaining-percent, `100 − x`); для наших четырёх: Codex/Kimi/GLM/OpenRouter — «использовано», но покрыть тестом поля каждого, чтобы дрейф был виден.

### Pitfall: ATS/таймауты по умолчанию
**Prevention:** ATS не ослаблять (все хосты HTTPS); таймаут запроса 10–15 c и общий бюджет опроса — чтобы 4 параллельных запроса успевали внутри жизненного цикла `getTimeline`; при зависании провайдера — снапшот кэша, а не вечное «обновляется».

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Парсеры «под текущий ответ» без фикстур | Быстрый первыйSuccess | Каждый drift провайдера — ручная почка в рантайме | Never — фикстуры с Ф-1 |
| Токен в UserDefaults «временно» | Быстрый прототип | Переписать хранение + переспросить токены у пользователя | Never (ограничение проекта) |
| Виджет сам ходит в сеть и читает Keychain | Не проектировать App Group | Нарушение ограничения проекта + класс проблем ACL | Never — снимок через App Group |
| Ручной дубликат suite-строки в двух таргетах | Экономия 10 минут | Пустой виджет после переименования | Never — общий модуль констант |
| Refresh OAuth внутри приложения | «Полная автономность» | Разлогинивание Codex CLI (rotation race) | Only с single-owner локом; для MVP — never |
| UI-обновление меню-бара на каждый tick вместе с сетью | Кажущаяся живость | Лишний трафик, риск троттлинга провайдером | Разрешено: таймер рендера без сети |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| OpenAI/Codex `wham/usage` | API-ключ вместо OAuth access token; refresh параллельно с CLI | Bearer access token + `ChatGPT-Account-Id` + UA `codex-cli`; read-only, 401 → «запусти codex» |
| Kimi `coding/v1/usages` | Путь без `/v1`; путаница `api.kimi.com`/`api.kimi.ai` | Константа `https://api.kimi.com/coding/v1/usages`, Bearer API-ключ; weekly summary — отдельный верхнеуровневый `usage`, окна — в `limits[]` |
| Z.ai / bigmodel `quota/limit` | `Bearer` перед ключом; один хост на оба аккаунта | Голый `authorization: <key>` + `accept-language`; происхождение хранится рядом с ключом |
| OpenRouter `credits` | Показ `total_usage` как расхода периода | Баланс = `total_credits − total_usage`; 401 без ключа |
| Все разом | Последовательные запросы в `getTimeline` | Параллельно, таймауты, кэш-снимок при любой ошибке |

## Performance Traps

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Сетевые запросы в `getSnapshot` | Галерея/добавление висят, пустой preview | Кэш или семпл при `isPreview` | Сразу, на слабой сети |
| Опрос всех провайдеров каждую минуту из меню-бара | Задержки UI, риск 429 | Каденс меню-бара 1–5 мин + ручной refresh; кэш между | Неделя активного пользования |
| `reloadTimelines` на каждый аппдейт | Бюджет виджета исчерпан к вечеру | Reload только при изменении отображаемого | Через день-два |
| Записи таймлайна чаще 5 мин | Система схлопывает, бюджет тает | Шаг записей ≥15 мин, динамика через `Text(style:)` | Сразу после первой приёмки |
| Синхронное чтение/запись снимка на main thread | Подлагивания меню | Фоновая очередь/actor для App Group I/O | Растёт с числом окон |

## Security Mistakes

| Mistake | Risk | Prevention |
|---------|------|------------|
| Секреты в UserDefaults/логах/фикстурах | Токены утекают в бэкапы и публичный git | Только Keychain (`kSecUseDataProtectionKeychain`); grep-проверка перед пушем |
| Refresh-token redemption из второго процесса | Разлогин Codex CLI (`refresh_token_reused`) | Read-only позиция; refresh не реализуем в MVP |
| Виджет с доступом к Keychain | Расширение поверхности ACL-проблем и утечек | Виджет не получает токены вовсе: снимок без секретов в App Group |
| Вставка токена через общий буфер обмена в логируемое поле | Токен в системных дампах | SecureField, не писать в accessibility-лог, очищать буфер после вставки — не критично, но дёшево |
| Миграции «прочитал → удалил» для старых хранилищ | Потеря токена при сбое midway | Порядок CodexBar: «not found ≠ unreadable», чистить только после успешной записи нового места |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Ошибка сети/auth показана как 0% | Владелец думает, что лимит не тратился | Снимок кэша + «данные на HH:MM» + бейдж ошибки по провайдеру (прямоerебование PROJECT.md) |
| Нет возраста данных в виджете | Недоверие к цифрам | `fetchedAt` в каждой entry, текст «5 мин назад» |
| Проценты без подписи окна (5ч/неделя/месяц) | Непонятно, что скоро сбросится | Ключ окна рядом с процентом, отсчёт сброса динамической датой |
| Меню-бар блокирует клики на время опроса | Ощущение зависания | Сразу показывать кэш, индикатор обновления, данные подменяются по готовности |
| 401 в ряду с сетевой ошибкой | Пользователь «чинит» не то | Разные тексты: «протух токен → запусти codex/вставь новый» vs «нет сети» |

## "Looks Done But Isn't" Checklist

- [ ] **Виджет:** обновляется вне Xcode-отладчика на второй день — проверить интервалы без подключённого отладчика
- [ ] **Виджет после перезагрузки Mac** показывает кэш, а не placeholder — проверить холодный старт процесса виджета
- [ ] **Все 4 провайдера** переживают «выключи Wi-Fi» без ложно-0% — проверить каждый по отдельности
- [ ] **Протухший токен Codex** даёт внятную ошибку, а не 0% и не краш парсера — подложить битый/просроченный JWT
- [ ] **App Group entitlements** совпадают на обоих таргетах — `codesign -d --entitlements :-` обоих бинарей
- [ ] **Keychain** читается после пересборки с изменённой подписью — собрать второй раз, перезапустить, проверить отсутствие промптов
- [ ] **Спустя ~7 дней** приложение и виджет стартуют без provisioning-ошибок — или пересборка одной командой задокументирована
- [ ] **В git-истории** нет токенов (fixtures синтетические) — grep по `sk-`, `eyJ` перед пушем
- [ ] **Ответ с новым полем** (новый `unit`/`plan_type`) деградирует до «меньше окон», а не до ошибки — негативный тест
- [ ] **README** предупреждает про 7-дневную пересборку и отсутствие нотаризации — Ф-5

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Истёк профиль (7 дней) | LOW | Пересобрать одной командой `xcodebuild`; перезапустить приложение/добавить виджет заново |
| Keychain-айтемы недоступны после переподписи | LOW | Переввести токены в настройках; если промпты циклятся — удалить айтемы и создать заново в data-protection keychain |
| Refresh-токен скомпрометирован/reused | MEDIUM | `codex logout`/`codex login` заново; вставить свежий access token в приложение |
| Парсер сломался schema drift'ом | LOW | Сохранить сырой ответ в фикстуру, ослабить парсер, добавить тест |
| Ключ Z.ai от другого происхождения | LOW | Переввести ключ с правильной меткой хоста |
| Пустой App Group | MEDIUM | Сверить entitlements обоих таргетов, пересобрать оба, перелогиниться в виджет (удалить/добавить) |

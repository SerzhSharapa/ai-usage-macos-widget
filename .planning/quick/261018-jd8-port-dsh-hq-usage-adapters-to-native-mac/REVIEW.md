### CR-02 — HIGH / BLOCKER: Codex-пара не сохраняется атомарно; отказ очистки оставляет смешанный credential

**Файл:** `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/AiUsage/ProviderAccess.swift:381–402,487–489`.

**Точный контрпример статусов:** в своих слотах уже есть `(token A, accountID A)`. Импорт B: запись token B возвращает success (383), запись accountID B возвращает ошибку (386), обработчик вызывает удаление token B, но оно также возвращает ошибку — `try?` отбрасывает её (400). На диске остаётся `(token B, accountID A)`. Импорт сообщает неуспех и инвалидирует board, но не запрещает последующий refresh; когда чтение снова доступно, строки 488–489 строят GET с `Authorization: Bearer B` и `chatgpt-account-id: A`. Перезапуск также не устраняет смесь. Сервер может отклонить её, но клиент уже нарушил требование не смешивать идентичности; успешный ответ при доступе B к нескольким workspace тоже ничем не отделён.

Отдельно, если токен читается, а чтение существующего accountID даёт unavailable, строка 488 превращает ошибку в nil и отправляет запрос без выбранного accountID. Недоступность обязательной части выбранной пары не должна означать отсутствие этой части.

В catch также выполняется удаление старого Codex-токена даже тогда, когда **первая** запись token B не удалась и частичная новая пара ещё не создавалась. Это не сохраняет прежнее подключение при неуспешной замене, в отличие от обычного save.

**Исправление:** хранить access-token и optional accountID одной структурой в одном собственном DP-Keychain item, заменяемом одной успешной операцией; не менять старую пару при неуспехе. Альтернатива требует реально проверяемой транзакции/устойчивого карантина, а не best-effort delete. Ошибку чтения accountID обрабатывать как фиксированную ошибку Keychain без HTTP-запроса; только достоверное notFound допускает nil. Проверять сценарии отдельных отказов записи и отказа cleanup, не только чистый маппинг OSStatus. Реальные отказы на машине в этом ревью не провоцировались: приведён детерминированный путь обработки входных статусов, который код обещает обслуживать.

### WR-04 — MED / WARNING: повторное обновление после смены credential всё ещё теряется

**Файл:** `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/AiUsage/ProviderAccess.swift:283–290,343–345,411–412,449–458`.

**Точный пример:** единственный Kimi уже запрашивается с A. Пока GET ожидает ответ, save B успешно записывает ключ, инвалидирует и убирает строку. Созданный `Task { await refreshAll() }` попадает на `guard !inFlight` и выходит. Ответ A корректно отбрасывается эпохой. Текущий проход завершается с пустой строкой, следующий автоматический проход — лишь после `Task.sleep(5 min)`. Поэтому успешное подключение не начинает обещанный немедленный опрос, а UI/виджет могут показывать «Подключите аккаунты» при сохранённом B. Аналогично новый провайдер, отсутствовавший в исходном списке, пропускается.

### WR-05 — MED / WARNING: Keychain self-test способен выдать PASS при ошибке контрольного чтения

**Доказательство по коду / точные примеры:**

Ответ A приходит позже: ветка 362–366 без проверки актуальности credential снова вставляет строку; конец `refreshAll` снова сохраняет её. Даже ошибка вместо успеха воссоздаёт строку через `applyError`. На следующих проходах disconnected-провайдер пропускается, но воскресшая строка не удаляется.
2. В строке Kimi есть 80% от аккаунта A. Владелец сохраняет credential B. `saveCredential`/`applyImport` не очищают прежнюю строку. Если B получает 401, `withError` сохраняет именно 80% аккаунта A под текущим подключением B. Если A ещё запрашивался, запрос нового обновления отбрасывается `guard !inFlight`, а результат A принимается уже после замены credential.
3. `loadLastGood` загружает все строки без фильтра подключения; последующий проход не вычищает отсутствующие credential. Поэтому строка без собственного credential продолжает публиковаться после перезапуска.

Это конкретная последовательность доступных UI-действий и точек `await`, а не предположение о потоковой гонке: `@MainActor` не исключает чередование во время ожидания сети. `inFlight` предотвращает два refresh-прохода одновременно, но не устаревший ответ после disconnect/replace.

**Исправление:** держать app-local поколение credential каждого провайдера; менять его при save/import/disconnect, принимать ответ только при совпадении поколения и актуальном подключении. При замене аккаунта очищать прежнюю строку и её shared-cache представление; последнее удачное значение сохранять только внутри одной идентичности credential. При загрузке/публикации отфильтровывать disconnected-строки. После смены credential во время прохода запланировать один повторный проход, а не терять запрос. Проверка результата записи Keychain должна предшествовать признанию замены успешной. Не помещать токен/accountID в общий снимок.

**Адресная проверка после исправления:** задержанный ответ A → disconnect → завершение A не создаёт строку; A → B → 401 не показывает факты A; сохранённая строка без credential не попадает в новый снимок. Достаточно управляемого fake fetcher/store, без живого аккаунта.

### WR-01 — MED / WARNING: усечение текста ошибки не является редактированием секретов

**Файлы:** `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/Packages/UsageCore/Sources/UsageCore/ProviderAdapters.swift:403–410`; `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/AiUsage/ProviderAccess.swift:370–395`; тест `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/Packages/UsageCore/Tests/UsageCoreTests/ProviderUsageTests.swift:271–278,360–379`.

**Нарушенное свойство:** provider-controlled error text не должен переносить credential в общий JSON и виджет.

**Точный синтетический пример:** для `status=403`, `body=["message":"Invalid API key: sk-FIXTURE-SECRET-never-ship"]` функция возвращает `HTTP 403: Invalid API key: sk-FIXTURE-SECRET-never-ship` без изменений. Затем `applyError` помещает результат в `ProviderRow.error`, а `persistAndReload` сериализует его. Аналогично проходит `error.message` с `Bearer …`, account ID или URL. Лимит 120 символов ограничивает длину, но не содержание.

Наличие такого ответа у реального провайдера **не утверждается**: подтверждён отсутствующий барьер на границе произвольного сообщения. Тест отсутствия секретов сериализует заранее безопасные строки, а не путь error → snapshot, поэтому это свойство не доказывает.

**Исправление:** самый простой надёжный вариант — фиксированный текст по HTTP-статусу/ошибке разбора без произвольного `message`. Если детали обязательны, нужна отдельная проверяемая политика редактирования до записи/показа; одно удаление слова Bearer недостаточно. Добавить fixture с секретом именно в `message` и вложенном `error.message`, проверяя итоговый сериализованный снимок.

### WR-02 — MED / WARNING: возраст записи кэша выдаётся за возраст фактов; medium вообще не показывает возраст

**Файлы:** `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/Widget/TestWidget.swift:169–200,209–269,271–280`; `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/AiUsage/ProviderAccess.swift:378–395`.

**Нарушенное свойство:** возраст last-good данных должен оставаться честным при неуспешных опросах и различной свежести провайдеров.

**Точный пример:** `row.fetchedAt=10:00`, `row.error="Нет соединения с провайдером"`; неуспешный проход в 11:00 сохраняет прежние цифры, но создаёт `snapshot.writtenAt=11:00`. Small отображает относительное время 11:00, а не 10:00: старые факты выглядят только что полученными. Значок ошибки не объясняет возраст. В `mediumView` `footer` вовсе не включён, и ни одна строка не использует `fetchedAt`; у balance-строки с last-good ещё и ошибка скрыта веткой отображения суммы.

**Исправление:** использовать `row.fetchedAt` рядом с показываемыми фактами, либо явно подписанный консервативный возраст старейших отображённых фактов. При отсутствии успешного опроса показывать «данных ещё нет». Включить возраст и сигнал ошибки также в medium/balance. `writtenAt` допустим только с отдельной честной подписью «кэш записан», не как замена возраста данных.

### WR-03 — MED / WARNING: неизвестное окно исчезает в агрегате виджета

**Файл:** `/Users/serzhsharapa/hq/build/ai-usage-macos-widget/Widget/TestWidget.swift:155–166,182–190,222–228`.

**Нарушенное свойство:** неизвестный расход не должен скрываться за известным низким процентом другого окна.

**Точный пример:** строка Kimi с окнами `[UsageWindow(key:"5h",percent:nil), UsageWindow(key:"week",percent:10)]` допустима для legacy-парсера. `worstRank` правильно даёт 101 и поднимает строку наверх, но отрисовка затем делает `compactMap(\.percent).max()` и выводит зелёные `10%`. Неизвестный 5h не виден ни в small, ни в medium. Если все окна неизвестны, «—» работает; дефект именно в смешанном случае.

**Исправление:** перед агрегацией проверять наличие `percent == nil` и показывать «—»/«есть неизвестное окно» либо отдельный индикатор неполноты рядом с известным максимумом. Добавить fixture смешанного набора, а не только одиночного nil.

## Подтверждённые границы безопасности

- Импорт начинается только с явного `NSOpenPanel`, читает выбранный файл без записи; право app — `user-selected.read-only`, виджету оно не выдано. Парсер выбирает access/account поля, refresh не переносит. Codex API-key вместо OAuth отвергается.
- Реальный app-путь строит GET только через фиксированные адаптеры; GLM CN/Intl имеют разные provider/keychain слоты и фиксированные hosts. В UI нет custom-host ввода. Codex accountID передаётся только Codex-пробе. Делегат отменяет редиректы; сессия ephemeral, тела/заголовки явно не логируются и не сохраняются.
- `ProviderAccess.swift` включён только в app Sources. У widget entitlement нет сети, файлового импорта или keychain sharing; его фактический путь только читает снимок. Small и medium заявлены.
- OpenRouter требует одновременно `total_credits` и `total_usage`, иначе возвращает nil. Обычная ошибка сохраняет last-good timestamp/факты внутри строки; проблема CR-01 — границы смены credential, WR-02 — отображение timestamp.
- Один app-owned scheduler и guard refresh присутствуют; синхронные записи выполняются на MainActor. Это не исправляет устаревшие ответы CR-01.

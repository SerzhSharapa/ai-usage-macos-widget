# AI Usage Widget — подключение аккаунтов, настройка и пересборка

Подробная инструкция для владельца. Знание Swift не требуется: все шаги — это
установка Xcode, вход в Apple ID, несколько галочек в настройках проекта и одна
команда сборки. Названия пунктов Xcode приведены так, как они выглядят в
интерфейсе.

**Что получится в конце:** приложение «AI Usage» в строке меню, без иконки в
Dock, и виджет с лимитами подписок и балансами. Запросы выполняет приложение,
виджет только читает общий кэш. Пока аккаунты не подключены, показывается
«Подключите аккаунты», а не демонстрационные проценты. Проверено 18.10.2026.
После первичной настройки любая пересборка и переустановка — одна команда:
`bash scripts/build.sh`.

---

## 1. Что собирается и что появится

Из исходников репозитория собираются два продукта одной сборкой:

- **приложение** `AI Usage Widget.app` — ставится в `~/Applications`, показывает
  пункт в строке меню с подписками, балансами и настройками; иконки в Dock нет;
- **расширение-виджет** `AiUsageWidget.appex` — встраивается внутрь приложения
  и даёт виджет в Центре уведомлений.

Приложение опрашивает подключённые аккаунты при запуске, затем каждые пять
минут и по кнопке «Обновить». В App Group записываются только результаты
и время получения; ключей и токенов в этом файле нет. Виджет читает тот же кэш.

## 2. Установка Xcode (один раз)

1. Открой App Store, найди **Xcode**, установи (большая загрузка, несколько ГБ).
2. Один раз запусти Xcode и согласись с лицензией, если спросит.

Без Xcode ничего не соберётся: Command Line Tools, которые уже стоят на
машине, не умеют собирать приложения с виджетами и подписью.

## 3. Выбор Xcode для командной строки (один раз)

Открой Терминал и выполни:

```bash
sudo xcode-select -s /Applications/Xcode.app
```

**Зачем:** даже при установленном Xcode команда `xcodebuild` продолжает
указывать на Command Line Tools, пока ты явно не переключишь. Сборка будет
падать с ошибкой «tool 'xcodebuild' requires Xcode», хотя Xcode уже стоит —
это самый частый подводный камень.

Проверка: `xcode-select -p` должен показать
`/Applications/Xcode.app/Contents/Developer`.

## 4. Вход Apple ID в Xcode (один раз)

1. Xcode → меню **Settings** (или Preferences) → вкладка **Accounts**.
2. Нажми **«+»** слева внизу → **Apple ID** → войди своим личным Apple ID.
3. После входа в списке появится твоя личная команда (personal team).

Бесплатного Apple ID достаточно: App Groups и App Sandbox доступны бесплатному
тиру на macOS. Оплата аккаунта разработчика не нужна.

## 5. Подпись обоих таргетов (один раз)

1. В Finder открой файл `AiUsage.xcodeproj` — проект откроется в Xcode.
2. В списке слева (Project navigator) щёлкни по строке проекта `AiUsage`,
   в центральной панели выбери **TARGETS → AiUsage** → вкладка
   **Signing & Capabilities**.
3. Поставь галочку **Automatically manage signing** и в выпадающем списке
   **Team** выбери свою personal team (строка с твоим именем).
4. Теперь выбери **TARGETS → AiUsageWidget** (второй таргет!) и сделай ровно
   то же самое: **Signing & Capabilities** → **Automatically manage signing** +
   **Team** = personal team.

Важно: подпись настраивается отдельно для КАЖДОГО из двух таргетов — и
`AiUsage`, и `AiUsageWidget`.

## 6. Контроль capabilities (проверка галочек)

Файлы проекта уже содержат нужные capabilities — проверь, что они на месте и
не «расползлись»:

- **App Sandbox** — у обоих таргетов;
- **Outgoing Connections (Client)** — ТОЛЬКО у приложения `AiUsage`
  (нужен для будущих запросов к провайдерам; расширению сеть запрещена);
- **App Groups** — у обоих таргетов, ровно одна и та же группа.

Если Xcode при сохранении предложит «исправить» подпись отключением App Groups
или сменой команды на None — соглашаться нельзя: это меняет схему доступа.
Такой отказ — явный блокер, о нём написано в таблице «Действия при ошибках» ниже.

## 6а. Ожидаемая команда — ДО первой сборки (обязательно)

Приёмка не верит «согласованности самой себя»: если оба продукта по ошибке
подпишутся чужой командой — даже согласованной между собой, — проверка должна
это поймать. Поэтому нужен независимый источник правды: **TeamID твоей личной
команды, записанный тобой вручную до первой сборки**.

1. Создай в репозитории файл `scripts/expected-team.local` — одну строку: свой
   TeamID (10 латинских букв и цифр).
2. Где взять TeamID (любой из двух способов):
   - Xcode → **Settings → Accounts** → твой Apple ID → строка personal team:
     TeamID указан в скобках; или
    - поле `OU` (Organizational Unit) своего сертификата Apple Development
      в Связке ключей. Код в скобках в имени `Apple Development: <имя> (...)`
      может быть идентификатором разработчика, а не команды; не копируй его как TeamID.
3. Чего делать НЕЛЬЗЯ: брать TeamID из вывода `verify-install.sh` или из подписи
   собранного продукта — точка отсчёта обязана быть независимой от того, что
   проверяется.

Файл личный и в git не попадает (уже исключён `.gitignore`). Без него первая
же сборка откажет: preflight сообщит про отсутствие конфига, а staged-проверка
отвергнет сборку без ожидаемой команды.

## 7. Первая сборка и установка

В Терминале из корня репозитория:

```bash
bash scripts/build.sh
```

Что делает команда (полностью автоматически):

1. проверяет готовность: Xcode выбран, инструменты работают, есть сертификат
   «Apple Development», проект на месте, конфиг ожидаемой команды заполнен;
2. собирает оба продукта (Release) через `xcodebuild`;
3. копирует свежую сборку во временное имя в `~/Applications` и проводит
   ПОЛНУЮ проверку подписи: точные идентификаторы продукта (bundle id
   приложения и расширения, тип пакета, точка расширения WidgetKit — чужой
   продукт не принимается), Authority, TeamIdentifier обоих бинарей против
   твоей ожидаемой команды, точный набор прав, четырёхсторонняя сверка группы,
   целостность — и только после успеха;
4. корректно закрывает прежний экземпляр своего приложения (если запущен);
5. перемещает прежнюю сборку в Корзину и ставит новую;
6. запускает приложение.

**Ожидаемый результат:** приложение появилось в `~/Applications`, в строке
меню — новый пункт с диагностической панелью, иконки в Dock НЕТ. Подробный
лог каждой сборки (с вырезанными личными данными) лежит в
`~/Library/Logs/ai-usage/`.

## 8. Подключение аккаунтов и добавление виджета

1. Нажми значок приложения в строке меню → **Настройки…**.
2. Для готовых аккаунтов Kilo выбери **Импорт из файла (Codex / Kilo)…**.
   В системном окне нажми **⌘⇧G**, введи `~/.local/share/kilo/auth.json`
   и явно выбери файл. Для Codex CLI можно выбрать его `auth.json`.
   Файл читается только после выбора; исходный файл не изменяется. Поддерживаемые
   подключения сохраняются в Keychain этого приложения, refresh-токены не копируются.
3. Вместо импорта можно ввести ключи Kimi, GLM, OpenRouter и DeepSeek в защищённых
   полях. Для GLM выбери правильный регион: BigModel CN либо Z.ai.
4. Нажми **Обновить** в панели. Реальные цифры появятся только после успешного
   ответа провайдера; ошибка авторизации не означает расход 0%.
5. Открой **Центр уведомлений** → **Изменить виджеты**, найди **AI Usage** и
   добавь квадратный `systemSmall` или широкий `systemMedium`.
6. Сравни значения и время получения в панели и виджете. Уже размещённые виджеты
   сохраняются при пересборке; после изменения размеров галерею надо переоткрыть.

Секретный файл, его содержимое и ключи не отправляй в чат. Codex OAuth импортируется
как read-only снимок доступа: при 401 войди/обнови Codex в исходном клиенте и
повтори импорт. Автоматический refresh исходного аккаунта приложение не делает.

**Честные ожидания обновления:** после нажатия кнопки виджет перерисуется за
секунды-минуты, не мгновенно — система может объединять обновления, а фоновые
обновления виджетов ограничены бюджетом WidgetKit (~раз в 15–60 минут).
Гарантировать поминутную свежесть виджета нельзя — это ограничение платформы.

## 8а. Безопасная проверка ошибок

Отсутствие аккаунтов, ошибка авторизации, неизвестное окно, недоступный или
повреждённый кэш не являются нулевым расходом. Проверки парсеров и ошибок кэша
выполняются командой `swift test --package-path Packages/UsageCore` на фикстурах,
не на настоящих секретах. Не меняй права App Group и не удаляй пользовательские
файлы ради проверки ошибок. Старая Debug-инъекция контрольной записи не является
приёмкой продуктового кэша лимитов.

## 9. Повторная пересборка (обычный цикл)

Любая пересборка — та же одна команда из корня репозитория:

```bash
bash scripts/build.sh
```

Повторный вызов означает согласие на автоматическое закрытие текущего
экземпляра, замену сборки и запуск новой. Данные (контрольная запись в общей
папке) не очищаются — они живут вне бандла. Прежняя сборка перемещается в
Корзину, откуда её можно вернуть руками. Чужие приложения и файлы не
затрагиваются.

## 10. Срок подписи и действия после его истечения

Подпись личной команды не бессрочная. Никаких предположений вроде «семи дней»
здесь нет и не будет — срок измеряется фактически. После установки выполните:

```bash
bash scripts/verify-install.sh
```

Среди наблюдений (не ошибок) будут строки о сроке ПО КАЖДОМУ бинарю
(приложение и расширение): даты встроенного provisioning-профиля, а если
профиля нет — фактическая дата истечения сертификата подписи, извлечённого из
самой подписи. «Профиля нет» — это факт, а не бессрочность.

Действия: когда подойдёт измеренная дата истечения, просто пересобери и
переустанови той же командой `bash scripts/build.sh` — приложение запустится
заново с новой подписью. Проверка после фактического истечения (01-05) —
отложенное эксплуатационное наблюдение, не условие запуска виджета.

## 11. Диагностика

Если что-то не работает — собери отчёт:

```bash
bash scripts/diagnostics.sh
```

Отчёт содержит только безопасные данные: версии инструментов, ОС, КОЛИЧЕСТВО
сертификатов (без имён), строку регистрации виджета, права бинарей, имена
файлов в контейнере группы и хвост последнего лога сборки. Email, имена
identity, токены и ключи вырезаются до вывода и до сохранения. Имена файлов
общей папки показываются ТОЛЬКО когда установленная копия — действительно наше
приложение (совпадают bundle id и команда подписи с ожидаемой) и путь папки
канонический: для чужой/сломанной установки эта секция пропускается с
пояснением вместо выгрузки чужих имён. Отчёт сохраняется в
`~/Library/Logs/ai-usage/diagnostics-<дата>.txt` и его можно безопасно
переслать.

## 12. Действия при ошибках: симптом → причина → следующий шаг

| Симптом | Вероятная причина | Следующий шаг |
|---|---|---|
| Сборка: «Xcode не выбран активным developer dir» | xcodebuild указывает на Command Line Tools | `sudo xcode-select -s /Applications/Xcode.app` (раздел 3) |
| Сборка: «xcodebuild не выполняется» | Xcode не установлен или сломан | Переустанови Xcode из App Store, повтори раздел 3 |
| Сборка: «identity не найдена… Apple Development» | Не выполнен вход Apple ID или не выбран Team | Разделы 4–5: Accounts → «+» → Apple ID; Team в Signing & Capabilities у ОБОИХ таргетов |
| Сборка: «проект не найден: AiUsage.xcodeproj» | Команда запущена не из корня репозитория | `cd` в корень репозитория, затем `bash scripts/build.sh` |
| Сборка: «не задана ожидаемая команда» | Нет `scripts/expected-team.local` или он пуст | Раздел 6а: впиши одну строку TeamID |
| Staged-проверка: «team-несовпадение-с-ожидаемой» | Продукт подписан другой командой (не той, что в конфиге) | Проверь Team в Signing & Capabilities и TeamID в expected-team.local; источник TeamID — только Xcode/аккаунт |
| Staged-проверка: «identity-app / identity-appex / identity-подписи» | Продукт — не наше приложение (чужие bundle id/точка расширения, пусть и подписанные твоей командой) | Проверь PRODUCT_BUNDLE_IDENTIFIER обоих таргетов в проекте; чужой бандл в ~/Applications не должен стоять на каноническом пути |
| Остановка: «не удалось перечислить процессы» | Система не дала прочитать список/пути процессов — состояние неизвестно | Повтори команду; замена сборки в этом состоянии не выполняется намеренно |
| Остановка: «несколько процессов исполняют точный путь» | Запущено более одного экземпляра приложения | Закрой лишние экземпляры вручную (Activity Monitor) и повтори |
| Staged-проверка: «права-appex…» (лишнее право у расширения) | Расширению досталось сетевое/keychain-право | Проверь capabilities таргета AiUsageWidget (раздел 6): только App Sandbox и App Groups |
| Staged-проверка: «сверка-групп…» | Группа разошлась между таргетами/Info.plist | Убедись, что App Group одна и та же в обоих таргетах (раздел 6); пересобери |
| Xcode отказывается подписывать с App Groups | Автоподписи personal team не хватило | Это ЯВНЫЙ БЛОКЕР: НЕ отключай песочницу, НЕ меняй схему подписи. Собери `bash scripts/diagnostics.sh` и разберись по отчёту |
| Приложение установлено, но виджета нет в галерее | Приложение ни разу не запускалось после установки | `open ~/Applications/"AI Usage Widget.app"`, затем повтори раздел 8 |
| Виджет показывает «нет записи» | Тестовая запись ещё не создана | Открой панель в строке меню → «Записать тест» |
| Виджет показывает «запись повреждена» | Файл записи испорчен (редко) | Просто запиши тест снова — запись перезапишется |
| «Проблема контейнера» в обычной жизни | Общая папка недоступна — редкая реальная проблема | `bash scripts/diagnostics.sh` и смотри раздел контейнера в отчёте |
| Номер в виджете отстаёт от панели | Бюджет/объединение обновлений WidgetKit | Это ожидаемо (раздел 8): подожди или открой панель приложения |
| После замены старое приложение исчезло | Прежняя сборка перемещена в Корзину | Это сделано намеренно; при необходимости верни её из Корзины вручную |
